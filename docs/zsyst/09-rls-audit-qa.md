# 09 · تقرير تدقيق أمني: عزل المستأجرين (RLS) — Z-Syst على Supabase

**التاريخ:** 31 أكتوبر 2026 · **المشروع:** `atvttthrqsybjjwrbiyl` · **المكان:** `eu-central-1`

هذا التقرير يجيب على سؤال واحد: *هل العزل بين المستأجرين مُنفَّذ فعليًا وقت التشغيل، أم أنه فقط مهيّأ على الورق؟*

الخلاصة: **مُنفَّذ وتم إثباته بالتنفيذ الفعلي**، وليس بالاعتماد على قراءة السياسات.

---

## 1. لماذا لا يكفي «لديّ 137 سياسة RLS»

وجود سياسات في الكتالوج لا يعني أن الاستعلامات محجوبة. ثلاث ثغرات شائعة تُبطل العزل مع بقاء السياسات ظاهرة سليمة:

1. جدول واحد نُسي تفعيل `ROW LEVEL SECURITY` عليه ⇒ كل صفوفه مرئية للجميع.
2. جدول مفعّل عليه RLS لكن **بدون أي سياسة** ⇒ يُرفض كل شيء (خلل وظيفي، لا ثغرة) — لكنه يظهر كـ«محمي» في التقارير.
3. السياسات مكتوبة لـ `anon` أو بدور `public` ⇒ يمكن قراءتها بمفتاح anon دون تسجيل دخول.

لذلك بُني فحص آلي بدل المراجعة اليدوية.

## 2. ما تم تركيبه

Schema منفصل `zsyst_qa` (لا يمسّ `public`)، ودالة واحدة:

```
zsyst_qa.rls_audit() returns table(check_name text, passed boolean, detail text)
```

- `security definer` + `search_path = public, pg_temp` (مقاومة لاختطاف search_path).
- **سُحبت** صلاحية التنفيذ من `public` و`anon` و`authenticated`، ومُنحت لـ `postgres` فقط ⇒ لا يستطيع أي مستخدم نهائي استدعاءها.
- لا تكتب شيئًا ولا تحذف شيئًا: `SELECT` فقط على الكتالوج.

### القراءتان رقم 5 — وهما ليستا ثغرة
- `subscription_plans`: كتالوج أسعار عام، يُقرأ للعرض فقط. الإدخال يتم بالترحيلات (migrations).
- `businesses`: لا يوجد `INSERT` للعميل إطلاقًا. إنشاء المستأجر يتم من جهة الخادم/التجهيز (provisioning) بدور أعلى. وهذا هو التصميم الصحيح — ولو أُضيف `INSERT` سياسةً للعميل لأمكن لأي مستخدم إنشاء شركة وهمية.

## 4. اختبار الانتحال الفعلي (Impersonation)

السياسات تعتمد على `auth.uid()` المستخرج من `request.jwt.claims`. لذلك لا يكفي تفعيلها؛ لا بدّ من جلسة تحمل ادعاءات مستخدم. جرّبنا هوية `authenticated` بمعرّف غير موجود في `app_users`:

| الجدول | الصفوف المرئية | الحكم |
|--------|----------------|-------|
| `app_users` | 0 | ✅ |
| `products` | 0 | ✅ |
| `sales` | 0 | ✅ |
| `businesses` | 0 | ✅ |
| `subscription_plans` | 6 | ✅ مقصود (كتالوج عام) |

ثم محاولة كتابة عبر حدود المستأجرين:

```sql
begin; set local role authenticated;
select set_config('request.jwt.claims', json_build_object(
  'sub','00000000-0000-0000-0000-0000000000aa','role','authenticated',
  'business_id','999999')::text, true);
insert into public.products (business_id, product_name) values (999999,'x');
rollback;
```

**النتيجة:** `ERROR 42501: new row violates row-level security policy for table "products"`.

هنا **الخطأ هو دليل النجاح**: PostgreSQL رفض الكتابة. أي `INSERT SUCCEEDED` كان سيعني ثغرة تمنع إطلاق النظام لأي مستأجر.

> ملاحظة تقنية مهمة (أُصلحت): لا يمكن استخدام `SET ROLE` داخل دالة `security definer` — يرفضها المحرّك بـ `42501: cannot set parameter "role" within security-definer function`. لذلك فُصلت الفحوص الديناميكية عن الدالة، وتُشغَّل على المستوى الأعلى داخل `BEGIN … ROLLBACK` فلا يبقى أي أثر.

## 5. إعادة التشغيل

الملف القابل للتشغيل: `zs-repo/tools/rls-audit.sql`

```sql
select check_name, passed, detail from zsyst_qa.rls_audit() order by check_name;
```

يُعاد تشغيله:
- بعد **كل** ترحيل يضيف جدولًا أو يعدّل سياسة،
- وقبل تجهيز أي مستأجر جديد،
- وضمن بوابة الإصدار قبل النشر.

## 6. ما لا يغطيه التقرير (يحتاج موافقة/مفاتيح)

| البند | الحالة |
|-------|--------|
| اختبار عبر PostgREST بمفتاح anon حقيقي | ⏳ يحتاج `SUPABASE_ANON_KEY` (الموصّل يعيد هاش فقط) |
| اختبار جلسة Laravel كاملة عبر `SetSupabaseContext` | ⏳ يحتاج أول مستخدم في `auth.users` |
| دالة تجهيز مستأجر (`provision_tenant`) | ⏳ مؤجّلة حتى وجود مستخدم Auth حقيقي، لأن `app_users.id` مفتاح أجنبي إلى `auth.users.id` ولا يمكن اختبارها قبل ذلك |
| `research-control` edge function بـ `verify_jwt=false` | ⚠️ **تحتاج قرارك** — تغييرها إلى `true` قد تُعطّل مُستدعيها الحالي، لذا لم ألمسها |
